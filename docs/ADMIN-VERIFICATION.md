# Проверка базового администратора — 23 сентября 2026

Локальная проверка Windows, Node.js 22, PostgreSQL и встроенный браузер Codex.
Использованы отдельные вымышленные QA-аккаунты. Реальным пользователям право
администратора не выдавалось; существующие данные не удалялись.

## Автоматические проверки

- Финальный `npm.cmd run check`: ESLint без предупреждений, TypeScript,
  **101 клиентский тест в 18 файлах** и production-сборка Next.js — успешно.
- Полный серверный набор: **139 тестов в 9 наборах**, без пропусков и ошибок.
  Он включает 21 интеграционный сценарий администратора и существующие сценарии
  аккаунтов, связей, приглашений, занятий, тестов, оплат, обзора и уведомлений.
- После полного набора добавлена ранняя проверка admin-права до блокировки целевого
  аккаунта. Новая регрессия сначала получила timeout на прежнем коде, затем 403 на
  исправленном. Финальная сборка API и все **22 теста администратора** прошли.
  Повторная проверка прав и сессии под блокировками сохранена. Это **140 уникальных
  API-тестов** с учётом одного нового; вместе с клиентскими — **241 уникальный тест**,
  без двойного подсчёта повторного запуска административного набора.
- Миграция `009_admin.sql` применена к локальным dev/test БД. Контрольные суммы
  миграций 001–008 сохранены; автоматической выдачи прав в миграции нет.
- Клиентские регрессии сначала воспроизвели отсутствие методов API, затем прошли.
  Проверяются параметры поиска, кодирование ID, привязка ответа к аккаунту,
  передача версии/причины, отсутствие повтора конфликтующей операции, доступные
  переходы статусов, отдельное административное право и экранирование HTML.

Серверные сценарии проверяют обычные роли, сессию/CSRF/чужой аккаунт, безопасные
проекции данных, поиск и фильтры, пагинацию, защищённые аккаунты, CAS, запрет
недопустимых переходов, отзыв сессий и ссылок, конкурентные операции, атомарный
откат аудита, выдачу/отзыв права и защиту последнего администратора.

Отдельная регрессия воспроизвела реальную взаимоблокировку PostgreSQL: блокировка
учителя администратором одновременно с созданием уведомления этому администратору.
После замены соответствующих пользовательских блокировок на `FOR NO KEY UPDATE`
обе операции проходят. Изменения аккаунта по-прежнему сериализуются, а проверка
внешнего ключа получателя уведомления не создаёт цикл ожидания.

Команда выдачи прав проверена на запрет production, внешнего хоста и query-параметров
URI: установленный драйвер может переопределять хост через такие параметры.
Выдача/отзыв права также погашают старые ссылки подтверждения и восстановления.

## Проверка в браузере и через локальный API

API перезапущен с финальной сборкой: health `ok`, в OpenAPI пять административных
маршрутов. Повторная команда CLI grant для уже созданного QA-администратора завершилась
успешно без изменения прав. После перезапуска обновление статистики в браузере
получило актуальные данные. Локальный кабинет: `http://127.0.0.1:3000/account/`.

1. Обычный аккаунт не видит раздел администратора; отдельный QA-администратор видит
   статистику и административные функции после входа.
2. Поиск Student ID в нижнем регистре вместе с фильтром роли находит нужного ученика.
3. Карточка показывает технические метаданные и число сессий; учебных ответов,
   паролей и токенов в ней нет.
4. Блокировка с причиной уменьшает число сессий до нуля. Старый cookie получает
   401, новый вход заблокирован. После восстановления старый cookie по-прежнему
   недействителен, новый вход проходит.
5. Изменение из второй сессии создаёт конфликт версии. Исходная форма показывает
   ошибку 409 и сохраняет введённую причину; предусмотрено обновление карточки.
6. После успешного изменения фокус переходит на сообщение об успехе. Закрытие
   карточки возвращает фокус на актуальную кнопку пользователя в обновлённом списке.
7. Карточка собственного администратора не позволяет менять статус.
8. Деактивация требует отдельного флажка подтверждения. В браузере действие
   отменено до отправки; фактический переход проверяется интеграционными тестами.
9. Журнал отображает причины и переходы статусов; загрузка следующей страницы
   показывает оставшиеся записи.
10. На узком экране исправлено тесное расположение статистики. После исправления
    `clientWidth=341`, `scrollWidth=341`; горизонтальной прокрутки нет.
    Временное ограничение размера браузера снято.
11. В проверенном журнале браузера нет сообщений console error/warn.

Один запрос свойства поля через браузерный инструмент истёк по времени; сохранность
причины проверена последующим accessibility snapshot. Это не считалось успешной
проверкой самого запроса. Тестовый ученик оставлен активным, без деактивации.

## Обзор и границы проверки

Backend и SQL проверены отдельно от их реализации. Независимый обзор frontend
по ECC React/TypeScript/code-review помог исправить фокус после обновления карточки;
повторный обзор не выявил блокирующих замечаний.

Это локальная проверка: нагрузочные испытания, полный аудит WCAG, production-
процедура назначения администраторов и внешнее развёртывание не выполнялись.
Процент покрытия не измерялся. Изменения не закоммичены и не отправлены на GitHub.
