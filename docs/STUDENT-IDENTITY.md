# Единый ID ученика и общий кабинет родителя

Обновлено: 22 сентября 2026 года.
Основание: `E-Repetitor_Technical_Specification_v1.1_Final.docx`, версия 1.1
от 22 сентября 2026 года. Раздел 21 имеет приоритет при неоднозначности требований.
Документ описывает целевую модель; текущий прототип и его ограничения указаны в
[плане реализации](IMPLEMENTATION-PLAN.html).

## Подтверждено пользователем

- У ученика один постоянный ID на всей платформе.
- С этим ID ученик подключается к разным независимым репетиторам.
- Родитель добавляет ребёнка по ID и видит все его предметы, оплаты и результаты тестов.
- Повторная регистрация ученика для каждого преподавателя не требуется.

## Идентичность ученика

Профиль ученика существует на уровне платформы, независимо от преподавателя.
При подключении создаётся связь обучения; новый профиль ученика не создаётся.
Пример отображения ID: `STU-7K4M-9P2X` (иллюстрация, не действительный аккаунт).
Окончательные длина и формат определяются при реализации.

Используется отдельный случайный публичный ID с проверкой уникальности в БД;
внутренние связи используют UUID. Регистр при вводе Student ID не имеет значения.
ID сохраняется при смене преподавателя, имени, email и способа входа. Отображение
QR-кода с ID может упростить подключение, но не предоставляет дополнительных прав.
Сам ID не содержит ключа входа или разрешения на чтение результатов.

Учётная запись для входа и профиль ученика — отдельные сущности. Ученик владеет
своим аккаунтом и сам принимает Terms/Privacy; продуктовая модель не ограничивает
регистрацию по возрасту. Допускается username вместо email. Родитель не создаёт
профиль ребёнка и не получает управление аккаунтом через ParentConnection.

Если у ученика ещё нет аккаунта, преподаватель может создать временный `pending`
профиль. Ученик активирует его по конкретному одноразовому приглашению, сохраняя
ID и историю. При наличии аккаунта используют существующий Student ID;
автоматического объединения профилей по имени нет. Эти правила закреплены
в BR-001–003 и §25.1; recovery flow для username-only аккаунта ещё предстоит реализовать.

## Подключение к преподавателю

Основной путь по ТЗ v1.1:

1. Репетитор выбирает собственный предмет и вводит Student ID.
2. Система создаёт `pending` Enrollment. Преподаватель берётся из текущего
   контекста; принадлежность предмета этому преподавателю проверяется отдельно.
3. Ученик видит преподавателя и предмет и принимает или отклоняет запрос.
   Принятие создаёт активную связь; другой участник не подтверждает её за ученика.
4. Предмет появляется у ученика и у уже подтверждённо связанного родителя.

До подтверждения не открываются учебные данные. Переходы Enrollment:
`pending → active | rejected | expired`, `active ↔ paused`,
`active/paused → completed | cancelled`. Отказ и истечение запроса не дают доступа.
Запрос не является подтверждением зачисления и не создаёт начисления автоматически.

Повтор одного запроса не создаёт вторую одинаковую запись. У одного ученика могут
быть два разных преподавателя математики: их занятия, тесты и расчёты различаются
по преподавателю и записи об обучении, а не только по названию предмета.

## Добавление ребёнка родителем

1. Родитель входит в собственную учётную запись и выбирает «Добавить ребёнка».
2. Вводит постоянный ID. Это начинает запрос на связь, не открывая данные ребёнка.
3. Только сам ученик подтверждает или отклоняет запрос в своём кабинете (BR-004).
   Преподаватель и уже связанный родитель не могут подтвердить его вместо ученика.
4. После подтверждения ребёнок появляется в списке родителя вместе со всеми
   текущими и новыми предметами. Область доступа показывается перед подтверждением.

Первого и последующих родителей подтверждает ученик. Один ученик может иметь
нескольких родителей, а родитель — нескольких детей. Родитель подключается только
к существующему профилю. Преподаватель не выдаёт доступ к данным других преподавателей.
Формулировка guardian approval в раннем приложении A2 исходного ТЗ заменена
уточнённым правилом BR-004 и жизненным циклом из §22.

Приглашение активации/Enrollment имеет срок действия, однократное использование
и возможность отзыва; сервер хранит hash токена. Повторное принятие не создаёт
дубликат связи. ParentConnection имеет состояния `pending`, `active`, `rejected`,
`revoked`; новую связь после отзыва нужно подтвердить заново.
Доступ родителя проверяется при каждом обращении; отзыв связи закрывает доступ
ко всем предметам этого ребёнка. Кто может отзывать/восстанавливать связь — отдельное
решение до реализации управления семьями; знание ID не даёт такого полномочия.

## Что видит родитель

После выбора ребёнка отображается список его предметов с преподавателями.
Для каждого доступны расписание, посещение, опубликованные задания/результаты,
начисления, зарегистрированные платежи, остаток или задолженность и срок оплаты
в пределах настроек видимости финансовой информации.
Служебные заметки преподавателя в обзор не попадают.

Платежи и пакеты занятий относятся к конкретной записи об обучении. Долг одному
репетитору не погашается переплатой другому; несколько валют не складываются
в один денежный итог без отдельно определённых правил. Несопоставимые результаты
тестов не объединяются в общую «оценку знаний» ребёнка.

Предлагается показывать завершённые подключения в истории: прекращение занятий
сохраняет прежние результаты и расчёты, но закрывает выдачу новых заданий по
завершённой записи. Условия исправления старых записей нужно определить отдельно.

## Минимальная модель данных

| Сущность | Назначение |
| --- | --- |
| Учётная запись | Вход человека; один пользователь может совмещать роли |
| Профиль ученика | Глобальная идентичность и постоянный публичный ID; собственного входа ещё нет только у временного профиля |
| Предмет | Принадлежит одному преподавателю; одинаковое название у двух преподавателей не объединяет их данные |
| Запись об обучении | Профиль ученика, рабочее пространство преподавателя, направление, состояние подключения |
| Связь родителя | Родитель, профиль ученика, состояние подтверждения и область доступа |
| Приглашение/запрос | Участники, назначение связи, срок и состояние подтверждения |
| Учебные и расчётные записи | Занятия, назначения тестов, результаты, начисления и платежи конкретной записи обучения |

Авторизованный родитель читает разрешённые записи всех преподавателей через
активную связь с учеником. Проверка только равенства рабочего пространства
не подходит для этого кабинета. При этом преподаватель ограничен своим пространством
и своими записями обучения, даже когда знает общий ID ученика.

Глобальное имя и контакты ученика не становятся редактируемыми любым репетитором;
его локальные цели, уровень, цены и заметки хранятся отдельно. Не объединять профили
автоматически по имени, фамилии, телефону родителя или сходству данных: у родителя
может быть несколько детей. Исправление случайного дубликата требует отдельного
подтверждённого процесса переноса связей и истории.

## Проверки при реализации

- Один профиль подключён к математике и физике; один связанный родитель видит оба предмета.
- Два преподавателя одного предмета отображаются отдельно, без смешивания расчётов.
- Новый предмет автоматически появляется у связанного родителя после подключения.
- Ввод чужого ID без подтверждения не раскрывает контакты, результаты, оплаты и список репетиторов.
- Преподаватель одного предмета не может читать записи другого через общий ID.
- Преподаватель не создаёт Enrollment с чужим предметом.
- Родитель не создаёт профиль ученика и не подтверждает Enrollment или связь другого родителя.
- Только владелец профиля ученика принимает относящиеся к нему запросы.
- Родитель нескольких детей видит отдельные обзоры, без смешивания записей.
- Повторное подтверждение/отправка запроса не создаёт дубликаты.
- Просроченное, отозванное или уже использованное приглашение не выдаёт новый доступ.
- Отозванная связь родителя больше не открывает данные ни одного предмета ребёнка.
- Активация самостоятельного входа ребёнка и смена email сохраняют его ID и историю.

Технический ориентир: [OWASP — проверка прав при обращении по идентификатору](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html).
Непредсказуемый ID дополняет, но не заменяет проверку доступа к конкретной записи.
