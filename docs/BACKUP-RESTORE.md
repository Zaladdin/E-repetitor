# Локальная резервная копия и проверка восстановления

Команда создаёт копию `e_repetitor` и восстанавливает её в **новую** базу
`e_repetitor_restore_<UTC-время>_<случайный ID>`. Рабочая база служит источником
чтения. Команда не удаляет базы, не очищает таблицы и не перезаписывает существующую
базу назначения. При совпадении имени операция завершится ошибкой.

## Запуск

Требуются запущенный локальный PostgreSQL, зависимости API и уже установленные
утилиты `.local/pgsql/bin/pg_dump` и `pg_restore` (на Windows — `.exe`).
Ничего не скачивается и не устанавливается. `api/.env` содержит обычный
`DATABASE_URL` приложения. Разрешён только loopback, база `e_repetitor`,
непроизводственное окружение и URI без query/fragment.

Для создания новой базы нужна операторская учётная запись с правом `CREATEDB`
и правом назначать владельцем роль приложения. Её URI передаётся только через
переменную окружения `BACKUP_OPERATOR_DATABASE_URL`, должен указывать на базу
`postgres` **того же локального сервера и порта**. Используйте настроенное хранилище
секретов или локальное окружение; не вставляйте пароль в аргументы команды, Git,
отчёт или сообщение. Если переменная отсутствует, используются права роли приложения;
при недостатке прав проверка остановится до создания архива.

```powershell
Set-Location E:\E-repetitor\api
npm.cmd run backup:verify -- --source e_repetitor
```

На текущем хосте операторские учётные данные уже подготовленного переносного
PostgreSQL находятся в игнорируемом `.local/bootstrap-password.txt`. При выполнении
проверки они были прочитаны в память, без вывода в журнал. Права приложения
не расширялись. Команда намеренно не читает этот файл автоматически.

## Что проверяется

1. Операторские права, допустимый источник и границы путей.
2. Согласованный снимок PostgreSQL: `REPEATABLE READ READ ONLY` и
   `pg_export_snapshot`; `pg_dump` использует тот же снимок.
3. Custom-format архив, без владельцев и ACL. Пароль утилит передаётся через
   окружение дочернего процесса; libpq-переопределения из окружения очищаются.
4. Создание новой базы с владельцем — ролью приложения. Восстановление работает
   под этой ролью, с `--exit-on-error --single-transaction`, без `--clean`.
5. Сравнение количества и SHA-256 содержимого **каждой таблицы public**, включая
   связи, оплаты, результаты, аудит, сессии и таблицу миграций.
6. Сравнение колонок, ограничений, индексов, функций, пользовательских триггеров
   и enum-типов. Миграции дополнительно сверяются с файлами текущего checkout.

Строки хешируются в детерминированном порядке в UTC с чтением порциями.
Фоновые изменения исходной базы после начала снимка не входят в копию и не вызывают
ложного несовпадения. Проверка рассчитана на небольшую локальную базу: сортировка
всех строк имеет стоимость, а лимит операции утилиты — три минуты.

## Результаты и хранение

Результат находится в `.local/backups/pilot-*/`:

- `database.dump` — архив, содержащий также персональные данные и хеши секретов;
- `verification.json` — схема проверки, контрольные суммы, количества и время.

Новая папка закрыта для наследуемого доступа Windows: полный доступ у текущего
пользователя и SYSTEM; на Unix создаётся приватная папка. `.local/` игнорируется Git.
Отчёт терминала не содержит строк подключения, паролей, токенов или учебных ответов.

Архив, восстановленная база и частичные артефакты при ошибке сохраняются. Нельзя
подключать к копии обычный фоновый работник отправки писем: в ней восстановлена
очередь и сессии. Для чтения через отдельный API работник должен быть выключен.
Очистка таких баз — отдельное явное действие оператора; автоматического удаления нет.

## Границы

Это проверка восстановления локального логического снимка, а не production-backup.
Роли PostgreSQL, их пароли, ACL, настройки сервера, другие схемы, почтовый ящик и
внешние файлы в эту процедуру не входят. Текущая схема использует UUID; состояние
последовательностей для будущих serial/identity полей отдельно не сравнивается.

До внешнего пилота нужны ежедневные копии в отдельное защищённое хранилище,
срок хранения, ответственный оператор, согласованные RPO/RTO и повтор этой проверки
на staging. Расписание и внешние сервисы этим этапом не устанавливаются.
Фактический результат: [проверка пилота](PILOT-VERIFICATION.html).
