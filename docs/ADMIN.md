# Базовый кабинет администратора

Этап реализует административную основу из §13 ТЗ: статистику, поиск пользователей,
управление доступом и журнал критических действий. Раздел «Администрирование»
появляется в личном кабинете после выдачи права оператором и нового входа.

## Возможности

- Общие количества пользователей, подключений, занятий и тестов. Активность
  пользователя означает статус аккаунта, а не присутствие онлайн.
- Поиск по фрагменту email или Student ID без учёта регистра; фильтры по роли
  и статусу. Символы `%` и `_` воспринимаются буквально. Пагинация по 20 строк.
- Карточка с именем, email, ID, ролями, датами и количеством действующих сессий.
- Блокировка, восстановление и деактивация с обязательной причиной (3–500 символов).
- Общий журнал критических событий и история событий, где пользователь является
  автором или непосредственным объектом действия. Это не полная учебная история.

| Текущий статус | Разрешённые действия |
| --- | --- |
| Активен | Заблокировать, деактивировать |
| Заблокирован | Восстановить доступ, деактивировать |
| Ожидает подтверждения почты | Деактивировать |
| Деактивирован или удалён | Изменения недоступны |
| Собственный аккаунт или любой администратор | Изменения через панель недоступны |

Блокировка и деактивация отзывают все сессии и неиспользованные ссылки
подтверждения/восстановления. Восстановление доступа требует нового входа.
Нельзя подтвердить чужую почту разблокировкой. Деактивация требует явного
подтверждения в форме; данные сохраняются, обратного действия в этой панели нет.
Физическое удаление аккаунтов, финансов и учебной истории не добавлено.

Версия статуса защищает от перезаписи устаревшей карточкой. При конфликте причина
остаётся в форме; нужно обновить статус и выбрать действие заново. Изменение статуса
и запись причины в аудит происходят атомарно. Подтверждение email тоже меняет версию.

## Выдача первого доступа локально

Право хранится отдельно в `admin_memberships`. Регистрация и кнопка добавления
роли предлагают только преподавателя, ученика и родителя. Миграция никому
не выдаёт административный доступ автоматически. Команда предназначена только
для локальной непроизводственной PostgreSQL, внешний хост и production запрещены.
Строка подключения должна указывать loopback и не содержать query-параметров:
драйвер PostgreSQL умеет переопределять хост через такие параметры.

1. Создайте обычный аккаунт и подтвердите email через Mailpit.
2. Оператор получает UUID именно этого аккаунта из локальной базы, например
   запросом `SELECT id,email,status FROM users WHERE email='account@example.test';`
   с точным email своего аккаунта, и проверяет статус `active`.
3. Из каталога `api` выполните:

```powershell
npm.cmd run admin -- grant <UUID-аккаунта> "Первоначальный администратор локального пилота"
```

4. Войдите в аккаунт заново: существующие сессии отзываются при выдаче права.
5. Для отзыва используйте `revoke` вместо `grant` с причиной. Отзыв последнего
   активного администратора запрещён. Повтор команды с тем же состоянием безопасен.

Операторские команды записываются в аудит с `actorId=null` и явной причиной.
Назначение администраторов через веб, изменение пароля, вход от имени пользователя
и автоматическое превращение первого зарегистрированного пользователя в admin
не предусмотрены. Production-процедура управления администраторами — отдельное
решение перед развёртыванием; эта команда не является production-инструментом.

## Доступ и данные

Сервер проверяет активную сессию и право администратора внутри каждой операции.
Клиентский `isAdmin` только управляет отображением и не даёт доступа к API.
Чужой `X-Account-ID`, отсутствие сессии или административного права отклоняются.
Обычные учебные API продолжают проверять собственную роль/связи; admin не получает
автоматического доступа к ответам, результатам, оплатам или личным заметкам.

Поиск и карточки возвращают только явные поля, без паролей, токенов и секретов.
Аудит содержит имя/ID автора, тип события, ID объекта, время и причину изменения
статуса. Детальные учебные payload в него не добавляются.

## API и миграция

Маршруты под `/api/v1`, все требуют сессию и административное право. Интерфейс
передаёт `X-Account-ID`; изменение также требует стандартную CSRF-защиту проекта.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/admin/overview` | Общие количества и время снимка |
| GET | `/admin/users?query=STU-&role=student&status=active&limit=20&offset=0` | Фильтрованный список; ненужные фильтры следует опускать |
| GET | `/admin/users/:id` | Техническая карточка |
| POST | `/admin/users/:id/status` | `status,reason,version` |
| GET | `/admin/audit?userId=UUID&limit=20&offset=0` | Журнал; `userId` необязателен |

Лимит 1–100, смещение 0–10000. Ошибки: 401 нет сессии, 403 нет права или
защищённый администратор, 404 нет пользователя, 409 конфликт версии/перехода.
Миграция `009_admin.sql` добавляет версию статуса, memberships и поля аудита.
Применённую миграцию не редактировать. При откате приложения таблицы и аудит
сохраняются; индексы перед production необходимо оценить на реальном объёме данных.
