# Приглашение нового ученика

Преподаватель может пригласить ученика, который ещё не зарегистрирован.
Если аккаунт уже есть, используется [подключение по Student ID](CONNECTIONS.html).
Автоматического объединения аккаунтов нет: это правило §25.1 ТЗ v1.1.

## Сценарий

1. Преподаватель выбирает свой предмет, вводит имя и email ученика и подтверждает,
   что ученик сообщил об отсутствии аккаунта.
2. В кабинете появляется временная запись. На указанный email отправляется
   одноразовая ссылка, действующая семь дней.
3. Ученик открывает письмо, видит преподавателя и предмет. Он сам вводит имя,
   задаёт пароль, принимает тестовые условия и явно подтверждает обучение.
4. Сервер за одну транзакцию создаёт аккаунт, постоянный Student ID и активный
   Enrollment. Получение секретной ссылки подтверждает email из приглашения.
5. Ученик входит с этим email и новым паролем. Преподаватель после обновления
   видит активацию и Student ID. Связь с родителем по-прежнему подтверждается отдельно.

Если email уже занят аккаунтом любой роли или статуса, активация не меняет его
имя, пароль, Student ID или связи. Получатель видит предложение войти в существующий
аккаунт и передать преподавателю Student ID. Контролируемое объединение через
поддержку пока не реализовано.

## Временная запись и доступ

До активации временная запись принадлежит только создавшему её преподавателю.
Она хранится в `temporary_students`, без User, глобального StudentProfile и Student ID.
Это реализация подготовительной записи из ТЗ, а не второй аккаунт ученика.
Имя в ней вводит преподаватель; окончательное имя своего аккаунта выбирает ученик.

Создание приглашения не выполняет наблюдаемого преподавателем поиска аккаунта по
email. Поведение одинаково для занятого и свободного адреса. Преподаватель видит
только введённые им данные и состояние собственного приглашения. Проверка конфликта
аккаунта выполняется лишь для получателя секретной ссылки при активации.

Публичный просмотр приглашения показывает только преподавателя, предмет и срок.
Email и имя получателя в него не входят. Токен передаётся в теле POST, из адресной
строки интерфейса сразу удаляется и остаётся только в памяти открытой страницы.
После перезагрузки нужно снова открыть ссылку из письма.

## Повторная отправка и отзыв

- Повтор создания ожидающего приглашения на тот же email и предмет возвращает
  существующую запись, без повторного письма.
- «Отправить снова» доступно для ожидающих и истёкших записей через минуту после
  предыдущего приглашения. Создаётся новый токен; старый больше не действует.
- Ожидающее приглашение можно отозвать. Истёкшее и принятое приглашения сохраняют
  свои конечные состояния; отзыв уже созданного аккаунта этой кнопкой невозможен.
- Срок семь дней — временное решение локального этапа. Время проверяет PostgreSQL,
  включая финальную запись принятия. Истёкшую ссылку нельзя активировать.
- В базе хранится только SHA-256 токена. Исходный токен не возвращается API
  преподавателю и не сохраняется в журнале приложения.

## Почта и ограничения

В локальном окружении письма находятся в [Mailpit](http://127.0.0.1:8025/).
Это перехватчик тестовой почты; сообщения не отправляются реальным адресатам.
В списке видны `queued`, `sent` или `failed` и число попыток доставки текущей ссылки.
`sent` означает передачу почтовому серверу, а не прочтение учеником.

Отправка выполняется после сохранения приглашения. Штатное завершение сервера
ожидает окончания отправок; аварийная остановка может оставить `queued`.
Автоматической постоянной очереди повторов из §25.3 пока нет: преподаватель
использует «Отправить снова». Повтор создаёт отдельную запись приглашения и сохраняет историю.
Исходные токены ради автоматических повторов в базе не хранятся.

Текущий тип приглашения — активация нового ученика. Дополнительные ссылки
`enrollment` для существующего ученика, username без email и support-объединение
остаются за рамками этого этапа. Уже работающий путь Student ID остаётся основным
для существующих аккаунтов.

## Запуск

Окружение описано в [инструкции аккаунтов](ACCOUNTS.html). После обновления кода
выполните `npm run api:migrate`, затем перезапустите API и интерфейс.
Новая миграция — `004_invitations.sql`; старые миграции не редактируются.
Проверки запускаются через `npm run check` и `npm run api:test` с отдельной тестовой БД.

Фактические результаты: [проверка приглашений](INVITATIONS-VERIFICATION.html).
