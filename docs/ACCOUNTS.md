# Аккаунты и локальный сервер

Серверная основа использует NestJS и PostgreSQL. Интерфейс входа находится на `/`
и `/account/`, а прежний прототип подключений с вымышленными данными — на `/demo/`.
Сервер не импортирует демонстрационные данные из браузера.

## Объём этапа

- Регистрация по email преподавателя, ученика и родителя, подтверждение почты.
- Вход, обновление сессии, выход с текущего устройства или со всех устройств.
- Восстановление пароля через одноразовое письмо; смена пароля завершает сессии.
- Несколько рабочих ролей одного аккаунта и отдельные профили.
- Постоянный случайный Student ID, отличный от внутреннего UUID.
- Создание и чтение собственных предметов преподавателя через API.

Подключения существующих учеников и родителей также сохраняются в базе:
см. [сценарий Student ID](CONNECTIONS.html). Старое демо остаётся отдельным.
Регистрация ученика только по username, без email, требует отдельного восстановления
доступа и пока не включена. Расписание, тесты и оплаты остаются в плане разработки.

## Локальный запуск через Docker

Нужны Node.js 22.13+ и работающий Docker Desktop. Команды выполняются из корня
репозитория. На Windows можно использовать `npm.cmd`.

1. Скопировать `.env.example` в `.env`, заменить `POSTGRES_PASSWORD` случайным
   локальным паролем. Скопировать `api/.env.example` в `api/.env` и указать этот же
   пароль в `DATABASE_URL` (порт PostgreSQL — 55432).
2. Выполнить `npm ci --ignore-scripts` и `npm --prefix api ci --ignore-scripts`.
3. Запустить `npm run infra:up`, затем `npm run api:migrate` и `npm run api:build`.
4. В отдельных терминалах запустить `npm run api:start` и `npm run dev`.
5. Открыть [приложение](http://127.0.0.1:3000/) и
   [локальную почту Mailpit](http://127.0.0.1:8025/).

Используйте `127.0.0.1` и для интерфейса, и для API: `localhost` — другое имя
для проверки Origin и cookies. `NEXT_PUBLIC_API_URL` задаёт адрес API при сборке
интерфейса. API принимает запросы только от настроенного `WEB_ORIGIN`.

Mailpit перехватывает письма локально и не отправляет их в интернет. Для сценариев
можно вводить вымышленные адреса вида `teacher@example.test`. Ссылка подтверждения
придёт в Mailpit. Почта содержит секретные одноразовые ссылки и доступна только
на loopback-интерфейсе. Не публикуйте её порт наружу.

Доставка писем на этом этапе выполняется после сохранения аккаунта, без постоянной
очереди. При остановке API или сбое SMTP можно запросить письмо повторно.
Публичный ответ подтверждает приём запроса, но не обещает доставку. Очередь с
повторными попытками и мониторингом нужна перед пилотом.

`npm run infra:stop` останавливает контейнеры, сохраняя базу. Не используйте
`docker compose down -v`, если данные нужно сохранить.

На исходном компьютере Windows подготовлено окружение без Docker: PostgreSQL
18.6 и Mailpit 1.31.2 в `.local/`. Для повторного запуска —
`./scripts/start-local-infra.ps1`, для остановки — `./scripts/stop-local-infra.ps1`.
Скрипты ничего не скачивают и не меняют Windows-службы. В новой копии репозитория
используйте описанный выше Docker-вариант. Источники бинарных сборок:
[PostgreSQL / EDB](https://www.postgresql.org/download/windows/) и
[официальные релизы Mailpit](https://github.com/axllent/mailpit/releases/tag/v1.31.2).

## Проверка сценария

1. Зарегистрировать преподавателя, открыть письмо в Mailpit и подтвердить email.
2. Войти и создать предмет. Обновить страницу — предмет должен сохраниться.
3. Выйти и создать второго преподавателя — его список предметов должен быть пуст.
4. Зарегистрировать ученика, подтвердить email и сохранить показанный Student ID.
   ID остаётся прежним после повторного входа.
5. Добавить роль родителя к существующему аккаунту и переключить рабочий контекст.
6. Запросить восстановление пароля и воспользоваться письмом один раз.
   Старый пароль и ранее выданные сессии должны перестать работать.

Для автоматических integration-тестов при использовании Compose один раз создайте
отдельную БД: `docker compose exec postgres createdb -U e_repetitor e_repetitor_test`.
Укажите её в `TEST_DATABASE_URL` файла `api/.env`. Повторять создание уже существующей
БД не нужно. Тесты очищают только указанную тестовую БД и отказываются работать,
если её имя не оканчивается на `_test`.

## Хранение и границы защиты

Пароли хешируются Argon2id; в БД хранятся хеши токенов. Сессии используют короткий
access-cookie и обновляемый refresh-cookie с HttpOnly и SameSite=Strict.
В production cookies требуют HTTPS. Мутации проверяют точное значение Origin
и заголовок `X-Requested-With: ERepetitor`; CORS не разрешает произвольные сайты.
Владелец предмета определяется сервером по сессии, а не по полю формы.

Учётные данные находятся в игнорируемых env-файлах. Для integration-тестов нужна
отдельная `TEST_DATABASE_URL`. Тесты не должны запускаться на пользовательской БД.
Схема меняется версионированными SQL-миграциями; deployed-миграции не редактируются.
Перед следующими изменениями production-схемы требуется резервная копия и проверка
восстановления. Первый этап проверяется на новой локальной БД, не на production.

## Перед пилотом

Нужны опубликованные Terms/Privacy, финальные версии согласий, настоящий SMTP,
HTTPS-домен и размещение сервера с PostgreSQL. Тексты согласий в интерфейсе относятся
к тестовому окружению. Текущий этап не является готовым публичным сервисом.

GitHub Pages продолжает публиковать документацию: он не запускает NestJS и PostgreSQL.
Команда `npm run check` проверяет интерфейс и модель демо;
`npm run api:build` и `npm run api:test` — сервер. `npm run check:all` объединяет их.

Фактические результаты и границы проверки: [отчёт этапа](ACCOUNTS-VERIFICATION.html).
