# Решения и открытые вопросы

Дата: 22 сентября 2026 года.
Источник требований: `E-Repetitor_Technical_Specification_v1.1_Final.docx`,
версия 1.1 от 22 сентября 2026 года. Раздел 21 имеет приоритет при неоднозначности
более ранних формулировок ТЗ. Старые предложения проекта применяются только
в части, не противоречащей этим уточнениям.

## Решения для первого этапа

| Решение | Основание и граница |
| --- | --- |
| Самостоятельный профиль ученика | BR-001–003: ученик владеет аккаунтом; родитель подключается к существующему профилю и не создаёт его |
| Подтверждает только ученик | BR-004 и §22: ParentConnection подтверждает Student; Enrollment также принимает Student. Guardian approval из приложения A2 не используется |
| Предмет принадлежит преподавателю | §15: Subject содержит teacher_id; при создании Enrollment принадлежность предмета проверяется |
| Публичный ID не даёт доступа | BR-008: идентификация и подтверждение связи — разные действия |
| Next.js + TypeScript | Интерфейс прототипа и аккаунтов; серверный контур — отдельный NestJS API |
| Демонстрационные данные в браузере | `/demo/` хранит вымышленные примеры локально; серверные аккаунты используют отдельный API и PostgreSQL |
| Переключение рабочих контекстов | Целевая модель поддерживает несколько ролей User; демонстрационный переключатель не выполняет аутентификацию |
| Срок запроса Enrollment — 7 дней | Временное значение для демо и локального API. ТЗ требует TTL, но не задаёт длительность; production-настройку предстоит определить |
| Отзыв ParentConnection | В локальной реализации связь может отозвать сам ученик или связанный родитель; повторное подключение требует нового запроса. Расширение прав поддержки — будущая задача |
| Серверная проверка каждого объекта | Клиентские доменные проверки не заменяют проверку роли, владельца и связи в API |

Регистрация любого возраста и самостоятельное принятие Terms/Privacy —
продуктовые требования ТЗ. Юридические тексты и consent-механика требуют отдельной
проверки перед публичным запуском, как предусмотрено §18.2.

## Решения для серверных аккаунтов

- Отдельный NestJS API и PostgreSQL. Параметризованный SQL через `pg` и
  версионированные транзакционные миграции; без ORM и автоматической синхронизации схемы.
- Первый способ входа — email и пароль для всех трёх ролей. Username для ученика
  остаётся требованием, но откладывается вместе с его отдельным recovery flow.
- Одна учётная запись может добавлять рабочие роли. Добавление роли само по себе
  не открывает доступ к чужим ученикам, предметам или семейным связям.
- Непрозрачные токены с серверным хранением хешей позволяют немедленно отозвать
  access- и refresh-сессии. Обновление refresh-токена одноразовое, повторное
  использование отзывает семью сессии. Клиент не хранит токены в localStorage.
- В разработке письма перехватывает локальный Mailpit. Секретные ссылки не
  возвращаются публичным API и не выводятся в прикладные логи.
- Согласия имеют тестовый контекст; перед публичным запуском нужны финальные
  документы и их версии. Пока используем вымышленные аккаунты.
- Docker Compose описывает стандартное окружение. На текущем Windows-хосте
  Docker/WSL не запускаются, поэтому для проверки подготовлены PostgreSQL 18.6
  и Mailpit 1.31.2 в игнорируемой `.local/`, без установки Windows-служб.

## Решения для сохраняемых подключений

- Запросы создаются только к существующему активному аккаунту ученика по точному
  Student ID. Общего поиска учеников по имени, email или телефону нет.
- Преподаватель выбирает свой предмет; ученик подтверждает Enrollment в своём
  кабинете. До подтверждения преподаватель видит ID и состояние запроса, без имени
  ученика и учебных данных.
- Родитель отправляет запрос; только ученик подтверждает ParentConnection.
  Активная связь открывает имя ребёнка и его активные предметы у разных преподавателей.
  Отзыв связи закрывает этот обзор; собственная история запросов остаётся без имени.
- В списках API требуется явный рабочий контекст: teacher/student для Enrollment
  и parent/student для ParentConnection. Все идентификаторы владельцев берутся из сессии.
- Повтор pending возвращает существующий запрос. Повтор активной связи отклоняется.
  После завершения или отклонения создаётся новая запись с новым подтверждением;
  старая запись не переиспользуется. При истечении Enrollment новый запрос получает новый TTL.
- Подтверждённую связь преподаватель может приостановить, возобновить, завершить
  или отменить. Completed/cancelled не возвращаются в active обычным переходом.
- У ParentConnection пока нет TTL: отдельное состояние истечения не определено
  в согласованном enum ТЗ. Это открытая задача перед публичным запуском.
- PostgreSQL обеспечивает ограничения принадлежности предмета и уникальности
  незавершённых связей. API проверяет доступ, сохраняет изменения транзакционно
  и пишет audit events. Row-level security в текущей схеме не включена.
- Временные профили и email-приглашения реализуются отдельно от уже существующих
  аккаунтов, по правилам следующего раздела.

## Решения для приглашений

- По §25.1 временная запись не объединяется с существующим аккаунтом автоматически.
  Раннее предложение о присоединении существующего аккаунта к такой записи уточнено:
  существующий ученик использует обычный запрос по Student ID.
- До активации хранится только `temporary_students` у преподавателя. User,
  StudentProfile и публичный Student ID создаются один раз при принятии приглашения.
  Это осознанное разделение подготовительной записи и глобального профиля ученика.
- При создании преподаватель подтверждает отсутствие аккаунта со слов ученика.
  Сервис не раскрывает, занят ли введённый email. Конфликт показывается только
  получателю секретной ссылки и не изменяет существующий аккаунт.
- Ссылка привязана к email, преподавателю и предмету. Получатель явно принимает
  условия и обучение. Это подтверждение ученика позволяет создать active Enrollment
  одновременно с новым аккаунтом; родительского доступа оно не создаёт.
- TTL семь дней и минимальный интервал повторной отправки одна минута — временные
  параметры локального этапа. Повторная отправка заменяет токен, история сохраняется.
- Реализован только тип `student_activation`. Ссылки типа `enrollment` и операции
  поддержки отложены; подключение существующего ученика по ID уже работает.
- У письма есть состояние и попытка доставки, но пока нет постоянной очереди.
  После аварийной остановки возможен ручной resend; raw token никогда не хранится в БД.

## Решения для индивидуальных занятий

- Создание и перенос доступны активному подтверждённому Enrollment и активному
  ученику. Отмена и закрытие посещаемости ранее назначенных уроков остаются
  доступны преподавателю при приостановке/завершении обучения.
- Местное время интерфейса — явно указанный пояс устройства. Сервер получает
  ISO со смещением или `Z`, хранение — `timestamptz`. Новые уроки только в будущем,
  длительность 5–480 минут; эти границы приняты для первого варианта.
- Пересечения интервалов одного преподавателя запрещены, соседние разрешены.
  Actor-lock сериализует операции одного преподавателя между процессами API.
  Редактор политики конфликтов, серии и группы отложены.
- Перенос переводит исходный урок в `rescheduled` и создаёт связанную замену
  с новым ID атомарно. История исходных дат сохраняется, удаления нет.
- Посещаемость фиксируется после окончания по часам БД. Исправление завершённого
  урока требует причины и отдельного события с предыдущими значениями.
  Версия записи защищает от перезаписи параллельных изменений.
- Повтор создания с тем же UUID и содержимым возвращает прежний урок. Изменённое
  содержимое с прежним UUID отклоняется. Клиент сохраняет ключ при сетевом повторе.
- Ученик видит свою историю подтверждённого обучения. Родителю пока доступны
  только активные Enrollment + ParentConnection и активный аккаунт ребёнка.
  Возврат родительского доступа к закрытой истории потребует отдельного решения.
- Приватные заметки, комментарии посещаемости и подробная история доступны только
  преподавателю. UI и сервер проверяют текущий рабочий контекст отдельно от ролей User.
- `billing_effect=manual` и `charge_applied=false`: посещаемость ещё не создаёт
  списаний или оплат. Уведомления о переносах/отменах также относятся к следующим этапам.

## Решения для тестов

- Три типа вопросов: один вариант, несколько вариантов, текст. Черновик может
  быть незаполненным; публикация требует вопросов, вариантов и корректных ключей.
  Редактирование создаёт следующий черновик, выданные версии остаются неизменными.
- Назначение относится к конкретным версии и Enrollment по тому же предмету.
  Новые назначения и попытки требуют active; уже начатую попытку можно завершить
  после закрытия обучения, пока действует её таймер. Архив не отменяет назначения.
- Срок сдачи мягкий (§22): отметка просрочки не запрещает сдачу. Таймер жёсткий,
  отсчитывается от старта по часам БД. Истечение сохраняет принятые ответы,
  расходует попытку и запрещает изменения; автоматической сдачи нет.
- Закрытые вопросы оцениваются по точному совпадению набора. Все текстовые,
  включая пропущенные, требуют ручной оценки. Результат отдельно публикуется
  преподавателем даже при полностью автоматической проверке (§22).
- Ключи по умолчанию скрыты; дополнительные политики — после сдачи, срока
  или публикации. Они применяются только к собственной сданной попытке ученика.
  Итоговые баллы и комментарии всегда ждут публикации. Родитель видит итог
  и общий комментарий, без вопросов, ответов и частных оценок по вопросам.
- Родительский доступ требует активных связи и обучения, как у занятий.
  При отзыве он закрывается. Ученик и преподаватель сохраняют свою историю.
- Для первого варианта установлены границы: 30 вопросов, 8 вариантов, 10 попыток,
  1–180 минут таймера, целые 1–100 баллов на вопрос. Ручная оценка допускает
  два десятичных знака; проходной балл необязателен и не превышает максимум.
- Версии ответов и черновика предотвращают потерю изменений из другой вкладки.
  Создание/назначение/старт идемпотентны по UUID; один активный старт на назначение.
  История изменений проверки сохраняется, опубликованные оценки пока неизменны.

## Решения для ручного учёта оплаты

- Уточнение пользователя: деньги передаются вне платформы, преподаватель
  самостоятельно ставит галочку «Оплачено». Платёжные провайдеры не подключаются.
- Первая часть — отдельные записи по Enrollment с понятным назначением,
  необязательной суммой и двоичным статусом. Название описывает период/пакет/урок;
  галочка относится к конкретной записи, а не ко всем отношениям с учеником.
- Сумма при наличии передаётся целым `amountMinor` и хранится как integer.
  Диапазон 1–999999999 минимальных единиц, валюты AZN/RUB/USD/EUR. Обе величины
  задаются вместе; введённые лишние десятичные знаки отклоняются без округления.
- Новая запись неоплаченная. Только владелец-преподаватель меняет статус.
  Снятие отметки и аннулирование требуют причины; запись, прежние значения,
  время и автор сохраняются. Оплаченную запись сначала переводят в неоплаченную.
  Аннулированная запись неизменяема, удаления через API нет.
- Назначение и сумма неизменяемы после создания. Ошибочную запись отменяют
  и заменяют новой. Версия записи предотвращает перезапись из другой вкладки.
  Повтор создания защищён UUID, смена статуса задаёт целевое значение.
- Создание требует active Enrollment и активного ученика; исправления старых
  записей разрешены при закрытом обучении. Родитель видит активные связи/предметы,
  ученик — свои принятые связи, как в остальных модулях. Причины и история приватны.
- §24 не отменён: частичные платежи, количественные пакеты и lesson ledger
  реализуются отдельно. Текущий журнал не меняет посещаемость и не списывает занятия.

## Решения для общего обзора кабинета

- Первая часть этапа 8 — сводный экран трёх ролей, без уведомлений и администрирования.
  Обзор читает существующие таблицы; новые таблицы и миграции не нужны.
- Авторизованный `GET /overview?role` использует `REPEATABLE READ READ ONLY`.
  Роль, действующая сессия, родительское согласие, счётчики и списки проверяются
  в одном снимке. `studentId` разрешён только родителю и не заменяет проверку связи.
- Родитель видит активные связи с активными аккаунтами детей и активное обучение.
  Учитель и ученик сохраняют свои исторические занятия, результаты и записи оплаты.
  Карточки предметов и счётчик активных учеников относятся только к активному обучению.
- Ближайшие занятия включают идущие scheduled и следующие 7 дней; в карточке предмета
  следующее занятие может быть позже. Посещаемость — фактические отметки за 30 дней
  по завершившимся completed/student_absent, без вывода о пропуске из пустой отметки.
- Родителю возвращаются исключительно опубликованные итоги. Счётчики проверки,
  неопубликованные попытки, вопросы, ответы, ключи, личные заметки и история исправлений
  в его обзор не входят. Все роли получают только краткие проекции, без приватных полей.
- Учителю показаны waiting_review и completed для проверки/публикации; ученику —
  доступные старты и живые попытки, включая начатые до закрытия обучения.
  Мягкий срок не запрещает попытку, серверный таймер учитывается без записей в БД.
- Списки ограничены 5 занятиями/действиями/результатами и 20 предметами; totals
  точные и считаются в БД. Ноль платёжных записей не означает полную оплату.
  Отменённые записи исключены, суммы разных валют не складываются.
- Фильтр ребёнка действует на обзор; существующие разделы ниже сохраняют свой
  общий контекст. Их формы не размонтируются при обновлении сводки. Обзор обновляется
  вручную, при возврате в окно и после успешных изменений текущего аккаунта;
  это не push-синхронизация между устройствами.

## Вопросы для следующих модулей

Пользователь попросил пока пропустить домашние задания. Модуль отложен,
его требования не отменены. Добавлена первая часть учёта оплаты — ручные отметки.

| Вопрос | Что уже определено | Что ещё решить |
| --- | --- | --- |
| Отзыв связи родителя | После revoked доступ прекращается; повторная связь требует нового подтверждения | Полный список уполномоченных участников, восстановление и работа поддержки |
| История Enrollment | Исторические данные сохраняются; завершённая связь не активируется обычным переходом | Видимость истории для ролей, исправления прошлых записей и повторное обучение |
| Истечение запросов | Enrollment и приглашения имеют TTL; токен приглашения одноразовый | Production TTL и повторная отправка; истечение ParentConnection не описано отдельным состоянием |
| Расширенная оплата | Деньги вне платформы; ручные записи/статусы готовы. §24 предусматривает пакеты | Частичные суммы, количественный остаток, сроки задолженности, переплата и истечение пакета |
| Поля пакета | §24 определяет lesson_count, total_price, paid_amount и ledger | Устранить дублирование purchased_lessons/lesson_count из ранней таблицы перед миграцией |
| Исправления платежа | Исходная история и автор изменения сохраняются | Согласовать corrected из lifecycle с enum confirmed/reversed и контрактом adjustment |
| Видимость финансов | Ручные записи видны своему ученику и родителю по активным связям; причины приватны | Настройки расширенных финансов и доступ к закрытой родительской истории |
| Username без email | Такой вход разрешён ученику | Recovery flow без предоставления родителю владения аккаунтом |

Эти вопросы должны быть закрыты до реализации соответствующих серверных
операций. Расчёт остатка пакетов и задолженности пока не входит в локальную версию.

## Уведомления — первая версия (23 сентября 2026)

- Пять типов: напоминание о занятии, перенос, отмена, назначение теста ученику,
  публикация результата ученику и подтверждённым родителям.
- В кабинете включены по умолчанию, email выключен; настройки независимы по типу
  и каналу, общие для ролей аккаунта. CAS защищает от потери изменений.
- Постоянная очередь PostgreSQL записывается вместе с бизнес-событием; Redis и
  внешние поставщики не требуются для этой локальной версии.
- Перед чтением/отправкой проверяется актуальная связь и первоначальное согласие
  родителя. Письма не содержат имён детей, предметов, оценок или ответов.
- Фоновый работник включается явно; на этом хосте только локальный Mailpit.
  SMTP вне транзакции, 5 попыток, аренда 2 минуты, backoff до 8 минут.
  Возможен повтор письма после сбоя между принятием SMTP и записью sent.
- Применённая миграция 008 неизменяема. Следующий шаг — базовый администратор,
  затем проверки пилота и восстановление резервной копии. ДЗ остаются отложенными.
- Подробности: [Уведомления](NOTIFICATIONS.html), [проверки](NOTIFICATIONS-VERIFICATION.html).

## Администрирование — базовый кабинет (23 сентября 2026)

- §13 реализован в пределах базового этапа: общие количества, поиск по email/Student
  ID, роль/статус, карточка технических метаданных, статусы доступа и аудит.
- Административное право отделено от публичного Role: таблица admin_memberships
  и isAdmin в Account. HTTP-выдачи права нет; локальная команда требует UUID
  существующего активного аккаунта и причину, отзывает сессии и старые ссылки.
- Доступ защищён на сервере при каждой операции. Статусы себя и других
  администраторов нельзя менять через панель; CLI не отзывает последнего admin.
- Active можно блокировать или деактивировать; suspended — восстанавливать или
  деактивировать; pending_verification — только деактивировать. Деактивация
  терминальна для этого UI, без физического удаления исторических данных.
- CAS status_version и причина обязательны. Подтверждение почты тоже меняет версию.
  Пользовательские блокировки берутся в порядке UUID до изменения сессий/токенов.
  `FOR NO KEY UPDATE` совместим с проверкой внешнего ключа получателя уведомления,
  сохраняя сериализацию изменений аккаунта. Наличие admin-права проверяется до
  блокировки целевого аккаунта и повторно вместе с сессией после получения блокировок.
- Учебные ответы, баллы, платежи и заметки не раскрываются администратору через
  карточки. Support-access и системные настройки остаются отдельным расширением.
- Миграция 009 additive, без автоматических привилегий; ранее применённые SQL
  неизменяемы. Следующий этап — сквозная проверка и резервное восстановление пилота.

## Локальная подготовка пилота (23 сентября 2026)

- §20.3 проверяется в согласованном объёме: без отложенного homework и автоматического
  списания пакетов, с ручными отметками оплаты. Регистрация/почта, два преподавателя,
  один ученик и подтверждённый родитель входят в единый HTTP-сценарий.
- Backup проверяется на согласованном read-only снимке локальной базы, restore —
  только в новую случайно именованную базу. Сравниваются таблицы и определения схемы;
  локальные архивы закрыты ACL и игнорируются Git.
- Обычная роль приложения не получает CREATEDB. Отдельный оператор того же
  локального сервера создаёт новую базу с владельцем — ролью приложения.
  После этого восстановление и проверка снова используют обычную роль.
- Внешнее размещение, SMTP, юридические согласия, ежедневное защищённое хранение
  копий, целевая нагрузка и участники закрытого пилота требуют отдельной подготовки.
  Локальный прогон не объявляется production/staging-приёмкой.
